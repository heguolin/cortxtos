# ADR 0008 — 检索调优以评估集为门禁，rerank 后置

**状态**：已接受（2026-09-19，grilling 第四轮裁定）

## 背景

文档量增长后检索质量是产品生命线，但"调优"没有数字就是玄学：RRF k、chunk 大小、jieba 粒度、标题加权……改一处可能坏另一处。rerank 模型（聚合平台 `/v1/rerank`）是明显的提速手段，但供应商支持情况未验证，且无基线无法证明其收益。

## 决策

**评估集先行**：建 20~30 条中文问答对（`eval/eval-set.json`，query → 期望文档，从真实会话挑选 + 人工标注），`pnpm eval` 输出文档级 Hit@1/@3/@6（期望文档进前 k 名即命中，不看 chunk）。**一切调参（RRF k、每路召回数、chunk 参数、分词粒度、heading_path 加权）必须附评估集前后对比**。rerank 为第五类 ModelProfile（`kind: rerank`），**仅当 top3 命中率 < 80%（初始目标，可调）时才接入**；未配置 = 不重排序。

## 后果

- 调优从凭感觉变成跑分对比；评估集同时是回归护栏（改检索代码跑一遍即知是否退化）。
- 建评估集有人工标注成本（一次性 20~30 条，之后随知识库扩充）。
- rerank 不预先承诺供应商——接入前先确认中转站有可用的 rerank 模型。
- `pnpm eval` 会调用真实嵌入 API（消耗 token）；跑分频率低，成本可忽略。
